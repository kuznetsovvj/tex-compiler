# tex-compiler
Веб-сервис для удаленной компиляции tex файлов с иллюстрациями asymptote

## Развертывание

Деплой автоматический: push в `main` запускает `.github/workflows/main.yml`, который по ssh
заходит на сервер, забирает изменения, пересобирает образ приложения и перезапускает контейнер.

### Базовый образ нужно собрать вручную

`Dockerfile.app` начинается с `FROM texcompiler-base:latest`. **Этот образ автодеплой не собирает** - он уже должен существовать на сервере. В базовом образе лежит TeX Live с Asymptote, сбока занимает много времени и места, поэтому её вынесли из деплоя.

Собрать на сервере, в каталоге репозитория:

```bash
docker build -f Dockerfile.base -t texcompiler-base:latest .
```

Это требуется:

- при первом развертывании на новом сервере - иначе первый же деплой упадет на шаге `docker build` с сообщением, что образ `texcompiler-base:latest` не найден;
- после любого изменения `Dockerfile.base` - иначе оно просто не попадат в прод, и расхождение между репозиторием и сервером ничем себя не обнаружит.

### Что делает деплой

1. `git pull --ff-only origin main` - при локальных изменениях на сервере падает, а не создает 
merge-коммит;
2. `docker build -f Dockerfile.app` - пересборка образа приложения;
3. остановка и удаление прежнего контейнера, запуск нового с `--restart unless-stopped`, поэтому после перезагрузки сервера сервис поднимается сам. Контейнеру дополнительно монтируются `docker.sock` и каталог рабочих областей задач (секрет `MOUNT_TASKS_DIR`) - см. раздел про изоляцию компиляции ниже;
4. проверка живости: до 30 секунд опрашивается `http://127.0.0.1:<PORT_OUTER>/`, и при отсутствии ответа шаг падает, показав последние строки лога контейнера. Проверке нужен `curl` на сервере; если его нет, шаг об этом предупредит и продолжит без проверки;
5. `docker image prune -f` - удаление висячих слоёв после успешной проверки. Тегированные образы, включая `texcompiler-base:latest`, не затрагиваются.

### Изоляция компиляции

Каждый вызов `pdflatex`/`asy` выполняется приложением в одноразовом docker-контейнере
(`ContainerRunCommandBuilder`), а не в контексте самого приложения. У контейнера нет сети,
все capabilities сняты, включен `no-new-privileges`, rootfs только на чтение, запись
возможна только в `/tmp` (tmpfs с лимитом) и в примонтированный каталог задачи; процессы
идут от UID 65534 (nobody) с лимитами памяти/CPU/числа PID. Образ для контейнеров - тот же
`texcompiler-base:latest`.

Для этого app-контейнеру монтируются:

- `/var/run/docker.sock` - приложение вызывает `docker run`. В контейнер компиляции
  сокет не попадает. Сокет на хосте принадлежит `root:docker` (права 660), поэтому
  контейнер запускается с `--group-add <gid группы docker>` - workflow читает gid
  сам через `stat`. Без этого приложение под UID 1000 получило бы permission denied
  на сокете при первой же компиляции;
- каталог рабочих областей задач, общий с dockerd (секрет `MOUNT_TASKS_DIR`, значение
  вида `/var/lib/texcompiler-tasks:/tasks`). Путь на хосте и путь в контейнере должны
  совпадать, иначе dockerd не найдет каталог для монтирования. Приложение работает под
  UID 1000, поэтому на хосте один раз: `mkdir -p /var/lib/texcompiler-tasks && chown 1000:1000 /var/lib/texcompiler-tasks`.

Приложение работает не под root (UID 1000), поэтому все хостовые каталоги, смонтированные
внутрь для записи - storage, логи, каталог задач - должны принадлежать `1000:1000`:

```bash
sudo chown -R 1000:1000 <host-путь storage> <host-путь logs> /var/lib/texcompiler-tasks
```

Иначе первая же загрузка файла упадет с `UnauthorizedAccessException`, а раньше это
маскировалось тем, что приложение работало от root.

Локально и в CI, где docker недоступен, изоляцию можно выключить настройкой
`CompilationContainer:EnableIsolation=false` - тогда инструменты запускаются напрямую
(требуется локально установленный TeX Live с Asymptote).

### Секреты репозитория

`VDS_HOST`, `VDS_USER`, `VDS_SSH_KEY`, `PROJECT_PATH`, `MOUNT_STORAGE_DIR`, `MOUNT_LOGS_DIR`, `MOUNT_TASKS_DIR`, `PORT_OUTER`, `PORT_INNER`. Каталоги `storage` и `wwwroot/logs` монтируются томами с хоста и переживают пересоздание контейнера. Без заданного `MOUNT_TASKS_DIR` деплой падает на шаге запуска контейнера.

### Откат

Отдельного механизма отката нет. Деплой запускается любым push в `main`, поэтому вернуть прод в предыдущее состояние можно возвратом коммита:

```bash
git revert -m 1 <хеш_мержа>
git push origin main
```
